# 0005: Node 24 LTS instead of Node 26

- **Status:** accepted (supersedes the Node version in [0001](0001-runtime-and-toolchain-versions.md))
- **Date:** 2026-10-12

## Context

ADR 0001 pinned Node 26. Vercel, which hosts the web app (ADR 0003), doesn't offer Node 26 yet;
its newest runtime is Node 24. The repo has one Node version (`.nvmrc`) shared by the web app,
API, worker, CI and the server image, and we want local dev to match what runs in staging.

## Decision

- **Node 24 LTS everywhere**, pinned to 24.21.0 in `.nvmrc`. Root `engines` is
  `>=24.21.0 <25`; `apps/web` declares `"node": "24.x"`, which is what Vercel reads to pick its
  runtime. `@types/node` is 24.x to match.
- **Everything else from 0001 stands.** Node 24 strips TypeScript types by default (no flag, no
  warning), so the API and worker still run `.ts` directly with the same erasable-syntax rules.
  The codebase used no Node 25/26-only APIs, and the TypeScript target (ES2024) is supported.
- **pnpm is still installed with `npm i -g pnpm`**, even though Node 24 bundles corepack: Node 25+
  drops it, and this keeps the setup the same when we move back up. Vercel is the exception: it
  infers the pnpm version from the lockfile format (9.0, which it reads as pnpm 9/10), so the
  Vercel project sets `ENABLE_EXPERIMENTAL_COREPACK=1` to use the exact pnpm in `packageManager`.

## Consequences

- Node 24 is in maintenance LTS until April 2028, so there's no support pressure to move.
- Revisit when Vercel supports Node 26 (an LTS line from October 2026): bump `.nvmrc`, both
  `engines` fields and `@types/node` together.
